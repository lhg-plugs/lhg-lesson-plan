# lhg-lp-audit：教案审计方法论

> 目标：用"机器查结构 + 人查实质"的两层筛子，保证交付的每份教案都经得起推敲。
> 核心纪律：**blocker 清零才能说"备好了"；为清零改规则是作弊。**

## 1. 何时使用

- 教案写完准备交付前 → 必须跑本 skill
- 接手别人写的教案想快速找毛病 → 跑本 skill 第 3-5 步
- 公开课/赛课前终审 → 跑全量（含第 5 步人工评审）
- 只想生成教案不想自查 → 不许跳过本 skill，这是插件的硬门

## 2. 输入与输出

- **输入**：教案 Markdown（按本插件章节结构写）+ 课件大纲（可选）
- **输出**：自查报告，含：脚本发现（blocker / warning / nit 明细）+
  人工评审结论（通过 / 不通过）+ 需人工处理项清单

## 3. 第一步：跑确定性审计脚本

```bash
python3 <插件目录>/scripts/audit/lesson_audit.py --target <教案目录> --format text
```

脚本零第三方依赖，规则分五大类（规则 ID 与说明见脚本头部注释）：

| 类别 | 查什么 | 典型 blocker |
|---|---|---|
| 覆盖率（COV） | 知识点清单里的每项是否被教学环节覆盖 | 有知识点完全没人讲 |
| 课时（TIME） | 环节时长总和是否等于课时总长、单环节是否畸长 | 总和差 2 分钟以上 |
| 对齐（ALIGN） | 高阶目标是否有高阶活动支撑 | —（warning） |
| 术语（TERM） | 知识点清单内术语表述是否统一 | —（warning） |
| 评价（EVAL） | 有没有评价设计章节、内容是否充实 | 整节课没有评价环节 |

分级定义：

- **blocker**：必须修，不修不许交付；commit 前 hook 会拦截。
- **warning**：修掉，或写豁免理由（为什么这次可以例外）。
- **nit**：顺手修，不修也要在报告里列出来。

## 3.5 审计脚本规则速查表（完整版）

| 规则 ID | 级别 | 查什么 | 触发条件 |
|---|---|---|---|
| LP-COV-001 | blocker | 知识点覆盖率不足 | 清单中有知识点未被任何环节覆盖 |
| LP-COV-002 | warning | 浅层覆盖 | 知识点只在导入/小结环节出现 |
| LP-TIME-001 | blocker | 课时分配失衡 | 环节时长总和与课时总长差 > 2 分钟 |
| LP-TIME-002 | warning | 单环节畸长 | 单个环节占比 > 60% |
| LP-TIME-003 | warning | 时长未标注 | 有环节没写分钟数 |
| LP-ALIGN-001 | warning | 目标与活动不对齐 | 高阶目标无高阶活动支撑 |
| LP-TERM-001 | warning | 术语前后不一致 | 清单内有近似重复的知识点表述 |
| LP-EVAL-001 | blocker | 缺评价环节 | 无评价设计章节或内容过少 |
| LP-SYLL-001 | warning | 缺课标对齐 | 无课标对齐章节或内容过少 |
| LP-OBJ-001 | warning | 目标不可观察 | 目标动词在可观察动词表之外 |
| LP-OBJ-002 | warning | 目标未分层级 | 目标未标注认知层级 |
| LP-OBJ-003 | nit | 目标过多 | 教学目标超过 6 条 |
| LP-ACT-001 | warning | 活动类型单一 | 环节只有讲授/讲解类动词 |

规则阈值（2 分钟误差、60% 占比、6 条目标）是经验值，
如需调整必须在自查报告里写理由，**不许静默改脚本**。

## 4. 第二步：分级处置

1. blocker 逐条修：修一条用脚本复查一条，确认清零。
2. 修不掉的 blocker（如需要用户提供真实学情、学校特殊规定）→
   列入"需人工处理"，**不许**为清零改脚本规则或阈值。
3. warning 修掉或写豁免理由；nit 顺手修。
4. 全部处理完再跑一遍脚本，确认 blocker 为 0。

## 5. 第三步：人工评审清单（脚本抓不到的）

脚本只查结构，以下一律人工过：

### 5.1 目标可测性

- 每条目标的"达成标准"真能在一节课里测出来吗？
- "正确率 80%"——靠什么测？随堂 5 道题还是作业？写清楚了吗？
- 目标里的动词和评价设计测的是同一件事吗？
  （目标说"设计实验"，评价却是选择题 → 不通过）

### 5.2 活动可行性

- 教具清单里的东西，普通教室 5 分钟能备齐吗？
- 分组方案在真实班额下跑得起来吗？（50 人班搞 12 组辩论 → 不通过）
- 实验/制作类活动写了安全与纪律提示吗？

### 5.3 时间现实性

- 新授环节有没有留"学生卡壳"的缓冲？（卡 3 分钟后面全塌）
- 活动"可砍环节"写了吗？（时间超了先砍什么，要有预案）
- 导入真的能在 10% 时间内收住吗？故事讲嗨了收不回来是常见翻车点。

### 5.4 内容诚实性

- 教案里引用的课标条款编号是用户确认过的吗？现编的 → 标 blocker 打回。
- 例子里的数据、史实有没有编造？（"某科学家说过……"要给出处或删掉）
- 课件大纲和教案的环节对得上吗？页码错位讲课时会乱。

### 5.5 学生视角

- 读一遍教案，假设自己是中等生：哪个环节会走神？哪个指令听不懂？
- 找出来，改到"中等生能跟上"为止。

## 6. 第四步：输出自查报告（模板）

```markdown
# 教案自查报告（<课程主题>，<日期>）

## 脚本审计
- blocker：N（已清零 / 剩余 M，见下）
- warning：N（已修复 N1，豁免 N2）
- nit：N

## 人工评审
- 目标可测性：通过 / 不通过（理由）
- 活动可行性：通过 / 不通过（理由）
- 时间现实性：通过 / 不通过（理由）
- 内容诚实性：通过 / 不通过（理由）

## 结论：通过 / 不通过

## 需人工处理项
1. ……
```

结论只能是"通过"或"不通过"，不许写"基本通过""大致没问题"。

## 7. 反模式（不要这么做）

- ❌ 脚本报 blocker，手动改脚本阈值让它变绿——这是作弊，不是修复
- ❌ warning 全写"豁免：时间紧"——豁免要有真理由，"时间紧"不算
- ❌ 人工评审只看一遍就说"挺好的"——按 5.1-5.5 逐项过，逐项写结论
- ❌ 报告结论写"基本通过"——只有通过/不通过两种结论
- ❌ 发现编造的课标条款编号，只改成"需核实"就放行——这是 blocker，必须让用户确认版本后重写

## 8. 自检与反馈

每次执行完本 skill，做一次轻量自检（不额外输出打扰用户）：

1. 脚本跑了吗？blocker 真清零了吗？→ 没跑就说"通过"是不许的。
2. warning 都有处置（修复/豁免）吗？→ 裸奔的 warning 下次会变成 blocker。
3. 人工评审 5 项都写了结论吗？→ 缺项补上。
4. 需人工处理项列清楚了吗？→ 不要让用户猜。

如发现本 skill 自身的方法论缺陷，按以下流程反馈：

- **标准冒烟用例**：拿 fixtures/plan-bad/plan.md 跑一遍，
  检查脚本埋点是否全命中、人工评审能否发现"评价测的不是目标说的"这类问题。
- **一键提 issue**：确认问题后，以 `[QC] <一句话问题>` 为标题、
  正文写清"复现输入 → 错误输出 → 期望输出"，
  提交到 https://github.com/lhg-plugs/lhg-lesson-plan/issues。
