# lhg-lp-design：课程设计总方法论

> 目标：把小白的一句话课程想法，变成一份"可讲、可测、可复查"的完整教案。
> 核心纪律：**目标没定不写环节，环节没对齐目标不交付。**

本 skill 是 lhg-lesson-plan 插件的总纲：定义备课的五个阶段与每个阶段的产出物。
课标对齐细节见 `lhg-lp-syllabus`，活动设计细节见 `lhg-lp-activity`，自查细节见 `lhg-lp-audit`。

## 1. 何时使用

- 用户说"帮我备一节《XX》的课"，主题只有一句话时 → 必须按本 skill 走完全流程
- 已有教案想重做一版（换学段、换课时、换评价方式）→ 走第 2、4、5 步的精简版
- 只想单独做课堂活动 → 直接用 `lhg-lp-activity`，不用走本 skill
- 用户已经给了完整教案只想体检 → 直接用 `lhg-lp-audit`，不用走本 skill

## 2. 输入与输出

- **输入**：一句话课程主题（可能很模糊，这是正常的）
- **输出**：四件套
  1. `目标—知识点对照表`（课标依据 + 知识点 + 认知层级 + 教学目标）
  2. `教案.md`（按审计脚本识别的章节结构写：课标对齐 / 教学目标 / 知识点清单 / 教学环节 / 评价设计）
  3. `课件大纲.md`（每页标题 + 要点 + 配图/活动建议）
  4. `自查报告`（脚本结果 + 人工评审结论：通过 / 不通过）

## 3. 第一步：澄清（最多 5 个问题）

### 3.1 提问原则

1. **先定边界再谈内容**：学段、课时、课标版本这三个问题优先，它们决定一切后续设计。
2. **一次 1-2 个**：不要一次性甩 5 个问题，用户会烦。
3. **不替用户做决定**：公开课还是日常课、要不要小组活动，必须问。

### 3.2 必问清单（按需取用，不超过 5 个）

1. **学段学科？**——"这节课是哪个学段、哪个学科的？（如：初中生物）"
   → 决定课标版本与语言深度。
2. **课时多长？**——"一节课 40 分钟还是 45 分钟？连排两节吗？"
   → 决定环节切分，所有环节时长总和必须等于它。
3. **课标/考纲版本？**——"按哪个版本对齐？（如义务教育 2022 版）"
   → 决定目标层级的上限；版本不确定时写"待核实"，不许编条款号。
4. **学生基础？**——"学生是零基础，还是已经学过相关内容？"
   → 决定导入深度与是否需要前测。
5. **评价方式？**——"这节课怎么算"学会了"？随堂测、作业，还是课堂表现？"
   → 决定评价设计的形态。

### 3.3 停止条件

- 5 个问题问完，或用户说"就这样，开始吧"，或信息已足够定目标 → 进入第二步。
- 用户中途改主题 → 回到本步重新澄清，不要带着旧目标硬走。

## 4. 第二步：逆向设计（目标 → 评价 → 活动 → 环节）

这是本 skill 的核心方法论，顺序不能反：

### 4.1 定目标（见 lhg-lp-syllabus 第 4 步）

每个目标必须同时满足三条：

- **有认知层级标注**：（识记 / 理解 / 应用 / 分析 / 评价 / 创造）
- **有可观察行为动词**：说出、解释、设计、评价……禁用"了解、掌握、体会"
- **有达成标准**："正确率 80% 以上""能独立完成"等，一节课内可测

### 4.2 定评价（先于活动）

在目标定下来之后、设计活动之前，先写评价设计：

- 每个目标对应至少一种评价方式（随堂检测 / 课堂观察 / 作业 / 互评）
- 评价测的必须和目标说的是同一件事（目标说"设计实验"，评价就不能只考选择题）
- 写出评价标准（什么算达标），不要只写"课堂检测"

### 4.3 定活动（见 lhg-lp-activity）

- 高阶目标（应用及以上）必须配高阶活动（实验 / 探究 / 讨论 / 辩论 / 项目 / 案例）
- 每个活动写清：时长、分组、指令话术、产出物、收束方式
- 活动总时长 = 课时总长 - 导入 - 小结 - 评价，倒排

### 4.4 写环节

标准五段式（可根据课型调整，但总数与时长必须闭合）：

| 环节 | 建议占比 | 作用 |
|---|---|---|
| 导入 | 10% | 激活旧知、制造认知冲突 |
| 新授 | 45% | 核心知识点的讲授与探究 |
| 练习/活动 | 25% | 应用与巩固 |
| 小结 | 10% | 学生自己说收获，不是老师重复 |
| 评价 | 10% | 随堂检测，对应目标逐条过 |

每个环节标注分钟数，**总和必须等于课时总长**（审计脚本会校验，差 2 分钟以上即 blocker）；
每个环节写明"覆盖知识点"（供审计脚本做覆盖率校验）。

## 5. 第三步：课件大纲

教案定稿后输出课件大纲，一页一行的清单体：

```markdown
## 课件大纲（共 N 页）
1. 封面：课程标题 + 一句钩子问题
2. 学习目标：3 条目标原文，学生能看懂的话
3. ……
```

要求：每页只讲一件事；文字页不超过 6 行；标出哪几页配活动（与教案环节对齐）；
不做视觉设计，只给内容与配图建议。

## 6. 第四步：自查（见 lhg-lp-audit）

1. 先跑确定性审计脚本（知识点覆盖、课时闭合、目标—活动对齐、术语一致、评价环节）。
2. blocker 清零才能交付；warning 修或写豁免理由。
3. 再过人工评审清单：目标可测性、活动可行性、时间现实性、评价闭环。

## 7. 反模式（不要这么做）

- ❌ 目标写"了解光合作用"——"了解"不可观察，换成"说出/解释/设计"
- ❌ 先设计好玩的活动再凑目标——顺序反了，活动必须服务目标
- ❌ 评价设计只写"课堂检测"四个字——测什么、怎么算达标，一概没有
- ❌ 环节时长加起来 52 分钟，课时只有 45 分钟——时间不闭合，课堂一定拖堂
- ❌ 知识点清单 10 个，一节课全讲——贪多嚼不烂，拆成两节
- ❌ 课件大纲和教案各说各的——页码与环节对不上，讲课时会乱

## 8. 自检与反馈

每次执行完本 skill，做一次轻量自检（不额外输出打扰用户）：

1. 是否问了超过 5 个澄清问题？→ 下次合并同类问题。
2. 是否有目标用了"了解/掌握"？→ 打回重写。
3. 环节时长总和是否等于课时总长？→ 用审计脚本复核。
4. 是否有知识点没被任何环节覆盖？→ 补环节或删知识点。

如发现本 skill 自身的方法论缺陷，按以下流程反馈：

- **标准冒烟用例**：用"初中生物《光合作用》45 分钟"走一遍本 skill，
  检查 5 问内能否收敛、目标是否可测、时长是否闭合、审计脚本能否全绿。
- **一键提 issue**：确认问题后，以 `[QC] <一句话问题>` 为标题、
  正文写清"复现输入 → 错误输出 → 期望输出"，
  提交到 https://github.com/lhg-plugs/lhg-lesson-plan/issues。
